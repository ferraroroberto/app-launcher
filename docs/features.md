# What it does, in one screen

The tab-by-tab feature reference, moved out of the README. Setup, running and the gate stay in the [README](../README.md).

The web UI has five tabs, plus **Settings** (six tabs forced 11px labels, so Settings, the rarely used one, moved behind a **⚙ gear** in every page header — tap any tab to leave it). Every tab opens with the same **page header**: the tab's name, one context line, the theme toggle and that gear, with a small **CPU reading** (`42%`) just left of the toggle. It answers "is the PC loaded?" from any tab: a muted number at rest, amber once CPU has stayed at or above 70% for about 30 s, red at or above 90%, and `–` (never `0%`) when the server couldn't take a sample. The reading never hides, at any width or with any status: when the header line's exceptions no longer fit beside it (two parts on a phone), the line wears each part's compact form instead (`1 stalled · 1 you` for `1 stalled · 1 needs you`, `12 Q · 3 you` for `12 questions · 3 needs you`), chosen by measuring the line in `home-head.js`, so no ellipsis cuts the exception. Tapping it opens a sheet with total CPU, memory used and the three busiest groups of processes over the last few seconds, by name and cores used (`python (pytest) 3.1 cores`, no paths or command lines). Processes sharing a name are one row with a count and their summed cores (`python ×16 · fleet-config-wt-1440  11.2 cores`: a burn or a pytest tree spread over many processes), the repo or worktree folder shows when the whole group runs in one, and an **Everything else** row holds the CPU the rows don't explain (small processes, kernel time) so the rows add up to the CPU line. It is cheap by construction: one shared sampler in the webapp reads every process's CPU time in a single Windows system call every 5 s, and only while a page is asking. `GET /api/system/load` answers from that cached sample, and the page polls it every 10 s, never while hidden.

On a **wide desktop window** (1100px and up, mouse pointer — the fleet's wide layout) the tabs move into an 80px **left rail**, icon over label, and the Board spans everything right of it, header included. The **Code tab becomes list-and-detail**: a session's view (Chat, or Terminal where it is in-page) opens in a pane beside the session list instead of covering it, the row it shows stays tinted, tapping another row swaps the view in place, and with nothing open the pane says so. A full-control session's terminal still opens in its own PC window. Leaving the Code tab closes the view. **Jobs** is list-and-detail the same way: a job's sheet docks beside the list, and with no job open the pane shows **This week**, the Schedule sheet's day-grouped fires. **Apps** becomes two columns, each scrolling on its own: on the left the Apps list, Scan for new apps and Trays (what you can start), on the right **Running** with each running app's **Open**, **Copy URL** and **Stop** as visible buttons, then **Other ports** inline (the same rows and confirmed stop as the phone's sheet), or one plain "Nothing running · N apps to start" line. Below 1100px, and on a phone or tablet at any width, the layout is unchanged: the tabs sit in the top control of the centred 772px column (floating bottom pill on the phone).

- **Coding** — opens with a one-line **summary head card** (the fleet's vendored `home-head` component): app icon + title, a status line that names only the exceptions in their tone colour (`1 stalled · 1 needs you`, the Board's own Your turn routing; worst tone first, the vendored `renderHeadStatus` sorts by severity) and otherwise the plain `N sessions` (the running-apps count lives on Apps and git on the Projects card), and the light/dark **theme toggle** pinned right — the same position as the other fleet apps. Then three cards: **Usage**, **Sessions** and **Projects**. In Projects, every project directory directly under your configured projects folder becomes a tile (no `.code-workspace` or `*-remote.bat` needed — the list is the directory listing, recomputed live; hide folders with a gitignore-style ignore list in Settings). Each project is an **action-row** (the fleet's vendored `action-row`): the **bare on-disk folder name**, with the leading **★ star**, and **tapping the row launches your favourite agent** (Settings → *Favourite agent*) in it. Every other agent, and every other project action, sits behind the row's one trailing **⋮** kebab. The agents:
  - **Claude Code** (`claude`), **Codex CLI** (`codex`), **Antigravity CLI** (`agy`), **GitHub Copilot CLI** (`copilot`), **Pi** (`pi`, on your Claude subscription via the Agent SDK), and **Grok Build** (`grok`, xAI's terminal agent) — each menu row bears the agent's icon. An agent is greyed out with a hint when its CLI isn't installed (detection: the command resolves on `PATH`). See [Installing the Codex CLI](installing-agent-clis.md#installing-the-codex-cli), [Installing the Antigravity CLI](installing-agent-clis.md#installing-the-antigravity-cli), [Installing the GitHub Copilot CLI](installing-agent-clis.md#installing-the-github-copilot-cli), [Installing Pi](installing-agent-clis.md#installing-pi), and [Installing the Grok Build CLI](installing-agent-clis.md#installing-the-grok-build-cli) below.
  - A trailing **GitHub icon** opens the project's open-issues list, sorted by last updated, in a new browser tab — no process spawned, no session created. The repo URL is derived from the project's `origin` git remote; the icon is disabled with a hover hint when the folder has no GitHub remote.
  - Each launch has **two modes** chosen by the **Detached** switch in the Projects card's **launch toolbar** (the model selector on one row, then **Detached** and **Resume** as the fleet's switch, accent when on — one reusable component, `launch-toolbar.js`, that Life › Skills mounts too; the launch-time toggles sit on the launch surface, not in the card's header). A **filter** field above the list narrows it by name as you type (the Apps list has one too), remembered per list on the device, with an empty-state when nothing matches; its trailing **☆ star** shows only your favourites. **Toggle off → full control:** the agent starts inside a **launcher-owned pseudo-console (ConPTY)** and the phone drops straight into a **live, fully interactive terminal** — real output, scrollback, typing, `Ctrl+C`, image paste. **Toggle on → detached:** the agent opens in its own console window on the PC; the launcher only *tracks* it (running-sessions list, killable from the phone) and it survives a launcher restart — including a full `tray.bat --restart`.
  - A second toggle, **↺ Resume**, reopens an existing conversation: with it on, the next agent tap launches that agent's **own native session picker** — `claude --resume`, `codex resume`, `copilot --resume` all show their list of recent sessions to pick from. (The launcher never builds its own session list; it only hands off to the agent's picker.) Antigravity has no picker flag, so its Resume **continues the most recent** conversation (`agy --continue`); Grok's bare `grok --resume` likewise reopens the working folder's **most recent** session. Resume is **orthogonal to Detached**: with Detached **off** the picker streams to the phone in a full-control terminal; with Detached **on** the picker renders in the **detached console window** on the PC (a real interactive console, so the list is pickable there) and the session shows as `☁️ detached` in the running-sessions list.

  - A **launch-model selector** leads that launch toolbar. It offers provider-qualified **Claude · Sonnet/Opus/Fable** and **Codex · Luna** choices (Terra, Sol and Astra are in the catalog but switched off by default, since Codex on a ChatGPT sign-in refuses them), remembers each provider's default, and sends the selected value when its matching agent button is tapped. Every model selector across Coding, Board, Skills, history, and agent settings uses the same keyboard-ready menu while preserving each surface's own catalog, availability, saved value, and launch payload. Settings › Launch defaults exposes the same server-owned catalog and model-compatible effort choices.
  - **Models in the dropdowns** — Settings › Launch defaults carries one switch per catalog model, grouped by agent. A model switched off leaves the Projects picker, the Life OS Skills picker, the Board dispatch picker and the per-agent Launch defaults picker at once; a saved default that is switched off moves to the first model still on for its agent. A running or resumed session keeps its own model. Stored as `hidden_models` in `config/webapp_config.json`, a *hidden* list so a model newly added to the catalog shows by default.

  - The first card, **Usage**, answers "can I launch?": its summary names the pace in its tone (`under pace`, `ahead of pace`, `nearly used`), its footer says what the context filter saved today, and a tap anywhere on it opens the Usage sheet. It holds the **usage meter**: a "Claude Code" heading row (only when both agents are shown — alone, the windows sit straight under the card title and a `stale`/`unknown` chip keeps a row of its own), then **5h** and **Week** rows (label, thin bar, percent, reset time) with a small **pace tick** on the week bar at how much of the week has elapsed, then a **Codex** row and, when switched on, a **Grok** row — Claude and Codex by default (Settings → *Usage meter* has one switch each for Claude, Codex and Grok; all off hides this card), read from fleet-config's shared snapshot contract through `GET /api/rate-limits`. The meter does not follow the model selector: the number you need before launching is usually the one for the agent you have *not* selected. **Colour follows pace, not raw percent:** a bar is blue while its window is on or under pace, amber when the week is ahead of the week elapsed, and red at 90% or more in either window. Grok shares no limits with scripts, so its row never draws a bar: it shows today's spend from Grok's own ledger, or `limits not exposed by Grok`. Tapping the meter opens the **Usage sheet**: the exact resets, the week elapsed, Codex's state, Grok's spend today, and the context filter's savings for today and the last 7 days. Codex reports several native buckets at the same duration, so each duration collapses to its fullest window, keeping internal bucket ids out of the UI; measured `0%` stays distinct from unknown, and a source that is absent, unsupported or erroring still renders its own degraded line rather than dropping out. Claude's shard is only rewritten when a session paints its statusline and expires after ten minutes, so an idle stretch routinely returns a bare `unknown`; the meter then keeps its **last reading, dimmed, with an `unknown` chip** instead of blanking the numbers you opened the tab to read — never presented as a current, confident value. A stale reading dims the same way with a `stale` chip; with nothing measured at all the state word (`unknown`, `unsupported`, `unavailable`) is kept as text. Codex refreshes through fleet-config's bounded native one-shot collector when its cached observation expires — now regardless of which agent is selected.

  - Git state is **always on** (not on demand): the launcher fetches `/api/claude-code/git-status` once at boot and re-polls every ~45 s while the Coding tab is visible in a foreground page (paused when the PWA is backgrounded), so every row carries it with no tap (quieter): `on <branch>` in the plain context line when it is parked off its default branch, and an amber **uncommitted** chip when the tree is dirty — amber, not red: it needs you soon, nothing is broken. The Projects card's summary counts the uncommitted projects, its footer says when git was last checked (`Git checked 3 min ago`), and the **refresh** icon in its launch toolbar re-runs the check now. The rows are the off-main list, so the old Git status button and its popover are gone.

  - **★ Favorites** — each row leads with a **star toggle**: tap to pin the projects you actually work on. Favorites sort to the **top** of the list (alphabetical within the favorites group, then the rest alphabetically), so the default view always surfaces them first while keeping every project one scroll away. A **★ Favorites** toggle in the Projects toolbar **filters the list down to only your starred projects** — one tap to hide the long tail when you just want the hot few, tap again to bring them all back. Favorites persist in `config/webapp_config.json` (`coding_favorites`, the same place as the ignore list — no extra file); the header filter is a client-side view that persists across reloads.

  - **⋮ Project menu** — the row's one kebab, the same floating icon + label menu as a running session's ⋮: a **Launch <agent>** row per visible non-favourite agent, **GitHub issues**, and three project actions:
    - **Open in VS Code** — opens that project in the local editor via its `<name>.code-workspace` file — a **sibling** of the project folder, directly under `projects_dir`, the layout VS Code itself already uses here — **creating that file first** with a minimal one-folder shape when it doesn't exist yet; an existing workspace file is opened, never rewritten. Deliberately *not* a coding-agent launch: no PTY, no session, nothing in Running sessions and no Stop button. The item greys out with a hover hint when the `code` CLI isn't on PATH (VS Code installs it through its own *Shell Command: Install 'code' command in PATH* step).
    - **Show changes** — a **read-only, phone-first view of the working tree**, so a red tile no longer means "open VS Code just to look". A full-screen overlay (same chrome as the transcript) lists every changed and untracked file grouped **Changes / Untracked**, each row with a status badge (`M` modified · `A` added · `D` deleted · `R` renamed · `U` untracked · `C` conflict), a green pip when the change is staged, the path, and `+N −N` counts; tapping a row expands its **unified diff** inline (GitHub "Files changed" style — added/removed lines tinted, long lines wrapped), fetched lazily per file and **capped at 200 KB** (the row says so and points at VS Code). Everything is measured against `HEAD` (or the empty tree before a first commit), so the list is "what a commit would contain"; a clean tree shows *Working tree clean*. A red or yellow name flags a row worth opening this for; the row itself launches, so the name is not a shortcut in. The item is hidden for a folder that isn't a git repository. A viewer only: nothing here stages, commits, or discards.
    - **Open folder** — opens the project directory in **Windows Explorer** on the PC. Nothing is tracked afterwards.
    - VS Code and Explorer are **local-machine** actions, like every Coding-tab launch: they open on the PC the launcher runs on, not on the phone that tapped them. The whole menu is hideable from the **Visible agents** list below under the `vscode` pseudo-id (an existing hidden list keeps working).

  - **Visible agents** — with six agent buttons plus VS Code plus GitHub plus the star, the tile's icon strip gets crowded on the phone, and most people only ever use two or three harnesses. **Settings › Launch defaults**' **Visible agents** list carries one switch per button (every registered agent, plus the VS Code and GitHub issues icons); flip one off and it disappears from every project row immediately, tap it back on and it returns. The list is **generated from the live agent registry**, so a newly added harness shows up in it automatically — nothing to configure per agent. The choice persists in `config/webapp_config.json` (`coding_hidden_agents`, a *hidden* list so new agents default to visible). The favorite star is never hideable, and hiding is strictly about **launch clutter** in the ⋯ menu (the model dropdowns follow **Models in the dropdowns**, not this list): a hidden agent's icon still appears on its running sessions and Board cards, so the app never misreports what's actually running.

  The **Sessions** card lists running sessions above the projects, on the shared two-line session row: an avatar holding the agent's icon with a **green badge while it is alive** (red if it should be up but is down; the chief wears a crown instead), the title, and one line of `folder · status · age · up uptime` (the status word and last-activity age are the Board's own, from one shared formatter, e.g. `working · 9m`; the word is left out where a chip already says it, nothing is shown when the Board status is unknown, and on a narrow phone `up uptime` is dropped first so the rest stays whole). Only an exception gets a chip — a session the Board files under Your turn says `needs you` (amber), a stalled one `stalled` (red), a detached one a neutral `detached`; a full-control session working normally shows nothing, and so does one whose Board status is unknown (`/api/claude-code/sessions` carries each session's `board_column`, `board_status` and `board_age_seconds`, computed with the Board's own routing, so this needs no extra poll). **The chief's row comes first**: when no chief runs it shows **Start** and **Resume** on the row itself, and its kebab carries **Restart** (while it runs) and **Chief settings**. Telegram channel sessions fold into one flat **Telegram** row (`N running`, with an amber `context N%` chip at 50% or more) that opens their read-only list. Each row has one **⋮ kebab** pinned to its right edge, which opens a floating menu of the row's actions: **⌨ Terminal** (full-control rows), **💬 Chat** (every row whose agent has a transcript reader), **✏️ Rename / link**, and **✕ Stop-and-kill** (always last). Tapping the kebab opens the menu and never the session; **tapping the row itself** opens the **session view** in the mode it was last viewed in (a full-control row starts in Terminal on the phone and in Chat on a desktop browser; a detached row of a readable agent opens in Chat). Stop asks the agent to quit cleanly with its own command so its shutdown hooks run, waits briefly, then force-terminates as a fallback. The Board tab's drill-down drawer offers the same four actions: Chat and Terminal on its row, Rename and Stop in its kebab.

  **Session view (Terminal ⇄ Chat)** — full reference: [docs/session-view.md](session-view.md)

  The session view is one full-screen overlay over the Coding tab with two modes and a shared bar (*‹* back, title, an icon-only **Terminal ⇄ Chat** toggle, 🔊 read-aloud, and a **⋮** menu with Rename · Copy link · Stop and kill, plus Hide steps / Load new / Reload in Chat, **Compact** for Claude and **Changed files** for every agent with a transcript reader). Switching modes never reconnects or reloads anything.

  - **Terminal** — the live PTY, see [Interactive terminal](interactive-terminal.md).
  - **Chat — reading** — the session's whole conversation as a phone-readable list: your prompts and the agent's replies expanded, tool calls / thinking / plumbing folded per run into one quiet step line each, read as its newest step's own description with a live timer while it runs (shown by default, its +N −M, failed count and duration never cut off; ⋮ → Hide steps for a plain exchange), a command step opening as a clean card (`$` command, highlighted, then its output), failed tool calls marked, an edit step (Edit, Write, MultiEdit, and the other agents' recognised edit tools) opening as its **diff** (added lines green, removed red, with a line-number gutter only where the harness recorded real numbers, Claude's own patch; a long diff shows its first 80 lines with **Show full diff** for the rest, up to 200 KB), a very long prompt or reply that arrives capped carrying **Show the rest** to load the full text in place (it stays expanded across the live refresh, a failed load keeps the capped text with a retry, and a plan card, whose text the entry route can't serve, keeps the plain "open the terminal" note), and a **live refresh** that appends what the agent writes without disturbing your scroll (only for the chat you are looking at). Older turns load in bounded pages, so a multi-MB session is never read whole. Reads Claude Code, Codex, Grok Build, Pi, Antigravity CLI and GitHub Copilot CLI histories.
  - **Changed files** — every file a session's edits created, modified or deleted, with A / M / D badges and `+N −M`, each opening into the session's own edits to it in order, in the Show changes panel. Folded from the transcript rather than git, so it still works once the work is committed or the worktree is gone. Works for Claude, Codex, Pi, Grok, Antigravity and Copilot sessions; the non-Claude diffs carry no line numbers, and Codex's are read from its `apply_patch` (direct or inside `exec`). An opened file has a **Diff | File** switch: File shows the file as it is now, rendered for its type (Markdown, pretty-printed JSON, code with line numbers and token colours for Python, PowerShell, JavaScript/TypeScript, HTML/XML, CSS, TOML/INI, YAML, shell, SQL and the C-style languages (a compact regex tokenizer, `syntax-tint.js`, five colour classes on the fleet's existing text tokens in both themes; a file over 2,000 lines or 100 KB, or an extension with no tokenizer, stays plain; the Diff view and Chat's step diffs take the same colours, each hunk read as its new and its old side, plain code on a changed line in the code colour with the `+`/`−` kept in the diff green or red, and the same size cut-off over the whole diff), plain text; up to 256 KB, only files the session edited), with its absolute path, a **Download** button (the file under its own name, same 256 KB limit and refusals as the File view; the saved text is the file minus a leading BOM), and a **⋮** menu: **Copy content** (File view, the raw file), **Copy diff** (Diff view, the patch as drawn), **Copy path**, and on the PC itself **Open on PC** (VS Code, else selected in Explorer).
  - **Chat — answering** — an agent's `AskUserQuestion` is a card you answer with one tap; a plan awaiting approval (`ExitPlanMode`) can be approved or sent back from the phone for a full-control session, checked against the terminal's screen right before anything is typed; `/resume` (or a `--resume` launch) is a searchable card that resumes the conversation you tap.
  - **Chat — sending** — the same composer as the terminal, for full-control and detached sessions. The toast says what actually happened (*Sent*, then — if nothing verified the submit — a 15 s look at the transcript that raises *Sent, but the agent hasn’t picked it up* and returns the text only when it finds nothing; *Sent, not confirmed* for a detached console, *Queued*, *Not submitted*, *Send failed*); Ctrl/⌘+Enter sends on a desktop keyboard. A detached session's Send types into its PC console and is unconfirmed by design.

  Every behaviour above, the per-agent limits (which agents record tool failures) and the detached-session caveats are in [Session view](session-view.md). Served behind the same Tailscale + passkey gate as the terminal.

  The per-agent launch defaults live in **Settings › Launch defaults** (not on the Code tab; the launch-time model and the Detached and Resume switches stay on the Projects toolbar, so launching never needs Settings). It holds the favourite agent, the Visible agents list and one row per agent ("Opus · high · auto") that opens that agent's sheet: a Claude Code subsection (model / effort / permission mode / verbose / debug), an Antigravity subsection (`--dangerously-skip-permissions` / `--sandbox` toggles), and a GitHub Copilot subsection (the `--allow-all` toggle). **Effort is per model:** the Effort row shows and edits the model selected above it, and a launch gets that model's effort — your override for it, else its catalog default (Opus `medium`, Sonnet and Fable `high`, the models' own documented defaults), else `high`. Choosing **Model default** clears the override; **Don't send** omits `--effort` altogether. Codex uses the same rule with its own per-model defaults, and so does Pi (every Pi model defaults to `high`, sent as `--thinking`). A global Pi effort saved before efforts were per model is carried the same way, so a Pi `medium` stays `medium` for every Pi model. A global Claude effort of `high` saved before efforts were per model is dropped on load (it cannot be told from never having chosen), and any other value is carried to every Claude model. Neither Antigravity nor GitHub Copilot has a launch-time model picker — pick the model with `/model` in-session. Both CLIs do have an effort flag (`agy --effort`, `copilot --reasoning-effort`), but with no model to key it on the launcher sends neither, so an effort it could not tie to the model actually running is never claimed. For Copilot the missing model is also deliberate: Copilot resolves a `--model` id against the **account's entitlement** at launch and silently falls back to `auto` when it refuses, so a Settings picker would assert a model the session was not running. Which ids a plan allows changes with the plan, so no list in this repo can predict them: the launcher sends nothing, and Copilot's own `/model` (session) and `/config model` (default) show live what the plan allows.

- **Apps** — every `*.bat` under your scan root that the classifier recognises as Streamlit, a FastAPI webapp, or a Cloudflare-tunnel script. The tab opens on its glance card, **Running**: each app launched from here is a row with its **kind avatar** (Streamlit gauge, webapp globe, tunnel cloud) wearing the green **alive badge**, and the context line "up 2h · :8501" ("binding…" until the port is bound). Tapping the row opens the app over Tailscale (from `tailnet_host`, greyed out with the reason when it's unset); its ⋮ kebab shows the pid as its header line and holds **Copy URL** and, last, **Stop**. The card's last row, **Other ports** ("N listeners not started here", or "Could not check" when the probe failed), opens a sheet with every port listener on the PC, helper services folded under their parent app, each row's kebab holding Open, Copy URL and **Stop process**; **Check again** is the sheet's one action. When nothing launched here is running the card says so in one line, with a footer noting only apps launched from here appear (a webapp restart forgets them; they then show under Other ports). Below it the **Apps** card is open by default: a filter, then one **action-row** per app with the same kind avatar, which wears the alive badge while the app runs (from the Running poll) or a tunnel's probe says up, and a red badge plus a danger **down** chip when a tunnel is down. An idle app row is one line, since the avatar already says the kind; a tunnel keeps "Tunnel" as its context line (an Up tunnel gets no chip, Up is normal). **Tapping a row** runs the bat with **no window on screen** (🚫👁 stealth, the default) — the phone-first case, where a console popping up on an unattended PC is pure noise — and its one **⋮** kebab names the kind as its header line ("Streamlit app", "Web app", "Tunnel") and offers **Launch visible**, which runs the identical command line in a fresh CMD window you can watch (⚡), **Rename**, **Copy path** (the bat path) and, last, **Remove** (always there; there is no Edit mode anywhere). Both launch modes spawn the same way (`cmd /k`, direct child), so a stealth-launched app still binds a port and still appears in **Running** with a working Stop. A request that names no mode launches visibly, so an older cached PWA bundle never goes silently invisible. A tunnel's live URL is never rendered as text (a cloudflared URL carries a `?token=…` and wrapped to three lines): the kebab's **Open link** and **Copy URL** carry it. The Apps card's last row is **Scan for new apps** (not in Settings › Folders), which walks the Apps folder and shows what's new in a checklist. The port probe runs every 5 s only while the Apps tab is up and the page is visible, and once when the tab opens. The page header reads "1 down" while a tunnel is down, else "N apps · M running", where N counts the Apps card's rows (trays excluded). The folded **Trays** card summarises "N · M autostart"; each row keeps the tray's **autostart switch** as its one leading toggle and says "running" while a launch from here is up and "starts at log on" when the switch is on (a tray the tray process started at log on is not tracked, so a row never claims "not running"). **Stop**, **Stop process** and **Remove** sit last in their row's ⋮ menu, after a divider and in the danger colour, and ask first through the vendored confirm sheet (a ✕ and one danger-tinted action), never the browser's native `confirm()`. Every destructive row-menu item app-wide, including a session's Stop and a job's Remove, gets that same last-after-a-divider treatment; no row shows a visible danger button. The chief's Kill and Restart, a Telegram session's Stop and the passkey Remove and device name ask in that same sheet too, so no native `confirm()` or `prompt()` is left anywhere. A first read of the Apps list, the Running and Trays cards, the Other ports probe, Life's skills or the Board that fails shows a one-line error with **Retry** instead of a blank list; a later poll that fails keeps the last list under a *Last updated 14:05 · live data unavailable* line.
- **Jobs** — one-shot Python scripts and scheduled jobs (`.py` or `.bat` targets), fired from the phone, the Stream Deck, or Task Scheduler through one shared executor with a uniform run history. The tab opens on its glance card, **Next up**: the next three distinct jobs as rows (the time, the job, "today · also 18:00 · Daily 06:00": a job firing again the same day folds into its row), each opening that job's sheet; the card's header opens the full 7-day **Schedule** in a sheet. Below it the **Jobs** card holds a search field, a sort icon button and **+ Add** (always there: there is no Edit mode), then one row per job on the shared anatomy: a job avatar whose glyph names the job's kind (a script, a web check, a shell) and wears the green alive badge while it runs, the name, one meta line ("in 5m · Every 15 min", "running now · Daily 03:00", "Was daily 07:00" when paused), chips for exceptions only (**failed**, **stuck**, **not firing**, **not confirmed**, **paused**), the last-7 sparkline as the trailing value (healthy runs muted so a failure is the only colour in it, a short dash for a run with no outcome), and one kebab with **Run now**, Pause/Resume, Dry-run check, Edit and, last, **Remove**. The page header reads "1 failing · 1 not firing" in their tones when so, else "N jobs".
  - **Ordering & schedule** — the list defaults to next-run order (ascending by each job's computed next-fire time, so imminent dailies float above weeklies and manual/paused jobs sink to the bottom), with the Sort and filter sheet (the sliders button in the search field) switching to A–Z (the choice persists). Each scheduled row's meta starts with a relative countdown (`in 3h`); a concurrent run is reported as `running now` instead, since it doesn't consume the next scheduled fire. The **Schedule** sheet shows the next 7 days as a day-grouped agenda (`Today` / `Tomorrow` / weekday), with dense minutely/hourly jobs collapsing to a "frequent" footer.
  - **Run history** — tap a row to open its **job sheet** (on a wide desktop window it docks beside the list as the detail pane): the job's details and flags, Kill stuck run when a live run is stuck, recent runs with pin and re-run, and the selected run's output, with **Run now** as the sheet's one primary action; a run started there is selected and its output streams in. A live selection streams over WebSocket, finalized logs load once. Jobs can preserve downloadable files (`JOB_ARTIFACT_DIR`), and a run can be pinned to survive normal retention. Switch it off to see and stop them like any other session. **Settings › Telegram → *Start Telegram sessions automatically*** (off by default) brings the bots back after a reboot: when the webapp starts, it waits up to 3 minutes for the session-host, then starts every ready profile that has no live session through the same code as **Start on Telegram** (so never a second session on one bot) — a fresh session in the profile's skill, on `channel_model`, with no PC mirror window. The launch adds `--channels plugin:telegram@claude-plugins-official` and `--settings <file>`, where the file is a two-line settings `env` block the launcher writes under its runtime-data directory (`channel-settings/<id>.json`) carrying only that profile's `TELEGRAM_STATE_DIR` (plus the relay entries below when a profile turns relay on) — Claude applies it to its own process, so the variable reaches that session's plugin server and no other, with no session-host change. The session is tagged `telegram:<id>` and shows as **Telegram · Health** on its Board card and Coding row; stopping it asks first. It always uses the normal permission mode (never bypass), runs in a phone terminal (no Detached) and on Claude only. **Settings › Telegram** (its row shows how many profiles are ready) is the read-only setup guide: ready/missing/unknown checks for the profile file, the life-os folder, the plugin (installed for life-os) and Bun, one Ready / Needs setup row per profile (skill found, token file present — a stat, never opened), the life-os skill folders a profile can bind, the six steps below (with an "If the bot doesn't answer" list), and a **Re-check** button. Its data is the same `GET /api/life-os/channels` payload, extended with booleans and skill names only — never a path, a token or a file's content; a check the server could not establish reads **Unknown**, not ready. **Setup, in order** — the launcher never reads a token, and creating bots and installing the plugin are yours:
    1. In @BotFather send `/newbot` to create **one bot per profile**, copy each token and, for group chats, send `/setprivacy` → Disable. **A bot token allows one `getUpdates` consumer**, so two sessions on one bot fight with `409 Conflict`; the launcher therefore refuses a second launch of a running profile (naming the session already running it).
    2. Install the plugin once in the life-os project (`/plugin install telegram@claude-plugins-official`); it needs [Bun](https://bun.sh) on the user `PATH` (`bun --version` prints a number). The card's checks show both.
    3. Give each bot its own state directory — `~/.claude/channels/telegram-<id>` by convention, created with `mkdir` — and put its token there yourself: create a file named exactly `.env` in it with the single line `TELEGRAM_BOT_TOKEN=<token>`, in an editor, so the token never passes through an agent chat (the plugin's `/telegram:configure <token>` would paste it into one). On Windows pick *Save as type: All files* in Notepad, or it saves `.env.txt`, which the plugin never reads. Sender pairing happens later, inside the profile's own session (step 6) — both plugin commands read `TELEGRAM_STATE_DIR`, which only that session has.
    4. Copy `config/channel_profiles.sample.json` to `config/channel_profiles.json` (gitignored, machine-local) and list each profile: `id` (lowercase slug), `label`, `skill` (a life-os skill folder, lowercase, exactly as the card's chips spell it) and `state_dir` (the step-3 folder as an absolute path that must exist, written with forward slashes; two profiles may not share one). Profile files hold paths and names only — never a token, chat id or user id. A row with a problem is skipped and the reason is shown on the card.
    5. **Make sure nothing else claims the token.** The plugin loads `<state_dir>/.env` into its environment only for keys that are not already set — *the real environment wins*. A `TELEGRAM_BOT_TOKEN` in Claude's `env` block (`~/.claude/settings.json`) or in the user/system environment is therefore inherited by every profile session, so every profile polls that one bot, never answers its own, and Telegram's `pending_update_count` for the right bot just grows. Remove it there and keep it where its own tool reads it (fleet-config's hooks resolve it from the process environment, then fleet-config's gitignored root `.env`, then `settings.json`, so its root `.env` is enough). Check without printing the secret, in PowerShell: `Select-String -Path ~/.claude/settings.json -Pattern TELEGRAM_BOT_TOKEN -Quiet` and `[bool][Environment]::GetEnvironmentVariable('TELEGRAM_BOT_TOKEN','User')` should both print `False`. Then give the plugin's **default** state directory, `~/.claude/channels/telegram/.env`, a `TELEGRAM_BOT_TOKEN=` line for a bot **no profile uses**: an ordinary (non-profile) Claude session in life-os starts the plugin too, with no state directory, and with no token it fails with `TELEGRAM_BOT_TOKEN required`. Claude Code **remembers a failed plugin start for about 15 minutes** under one shared server name (`plugin:telegram:telegram`), so every profile session started in that window skips the plugin (`Skipping connection (recent failure cached…)`) and the bot stays deaf. A plain session that does start will listen on that default bot — which is why it must not be a profile's.
    6. Tap **Re-check** (every row should read Ready), reload the Life tab and pick **Start on Telegram** from the bound skill's ⋮ menu; the plugin's server starts with the session. Then **DM the bot itself** — not a group; pairing only happens in a one-to-one chat. It replies with a 6-character code, valid for 1 hour (it repeats it at most once, then goes quiet). Inside that profile's terminal run `/telegram:access pair <code>`; the plugin confirms with "Paired!" on Telegram. **Pairing is per Telegram person, not per chat**: each extra person (say, a spouse) DMs the bot from their own account and you run `pair` with *their* code in the same terminal (or `/telegram:access allow <user id>` if you know their numeric id) — everyone paired shares that one session and its context. `dmPolicy` stays `pairing`, so a stranger who finds the bot only ever receives a code that you can ignore. **Groups** are ignored until you opt each one in with `/telegram:access group add <group id>` (and the `/setprivacy` → Disable from step 1 if it should react to every message rather than mentions).

    **If the bot doesn't answer:**
    - **No reply to `/start` or a message.** The plugin is not listening to this bot. In the profile's state directory, **no `bot.pid`** means the plugin never started with that folder (see the next bullet); a `bot.pid` with silence means another token overrides the folder's `.env` — repeat the step-5 checks. To confirm which bot a folder's token belongs to, stop the profile, set `$env:TELEGRAM_STATE_DIR` to the folder and run `bun server.ts` from the plugin's folder (`~/.claude/plugins/cache/claude-plugins-official/telegram/<version>`): it prints `polling as @<bot>`. A plain terminal does not carry Claude's `env` block, so this proves the token, not the override. Never run it while the profile is up — two listeners on one token fight.
    - **"failed to connect" or `Skipping connection (recent failure cached…)` when the session starts.** The 15-minute memory above. Wait it out, then stop and start the profile. The default-directory token from step 5 stops the plain-session failures that set it off.
    - **Paired, but no "Paired!" message.** The plugin delivers it by polling for an `approved/<your id>` file in the state directory; one left behind means the plugin server is not running.
    - **No code arrives.** You messaged a group rather than the bot's own chat, or it has already sent the code twice (the code lasts an hour).

    **Relay: a bot steers its own skill's other conversations (off by default).** Add `"relay": true` to a profile in `config/channel_profiles.json` (only a JSON `true` counts) and restart its bot. From the chat, the bot can then find one of its skill's earlier conversations, resume it, send it a message and bring the reply back, while it stays the only Telegram reader: it posts the reply with its own reply tool. A resumed conversation launches the ordinary Life OS way, with no `--channels`, no settings file, no bot label and no PC mirror window, so it never starts a second plugin server and never sees the bot's token. Profiles without the flag launch exactly as before, and their settings file is unchanged.
    - **The command set** is `scripts/telegram_relay.py`, run by the bot as `$LAUNCHER_RELAY_COMMAND <subcommand>` (the venv interpreter and the script, as absolute forward-slash paths): `find [query]` (the skill's conversations, newest first, or its search hits, each saying whether it can be resumed and which session already has it open), `resume [path]` (that conversation or the newest resumable one, on its own model; one already open is returned instead of launching a second), `steer <session> <text>` (sent once, never resent), `read <session>` (the last reply) and `ask <session> <text>` (steer, then wait up to 2 minutes for the finished reply). The first output line is always `STATE=<state>`.
    - **Identity and scope.** Every launch of a relay profile writes a new random token into that bot's settings `env` block (`LAUNCHER_RELAY_TOKEN`, beside `LAUNCHER_RELAY_URL`, `LAUNCHER_RELAY_PROFILE` and `LAUNCHER_RELAY_COMMAND`); the relay routes (`/api/life-os/channels/<id>/relay/*`) check it against that file, so a relaunch retires the old one and a webapp restart does not. The routes answer only the PC itself, and only while that profile's bot session runs. A target session must be alive, must not be a Telegram bot or the fleet chief, and must have one of the profile's own skill's indexed conversations open (matched by the capture header's session id); anything else is refused as `not_this_skill`. The token sets the skill, so no call can name another one. Any other local process can still use the launcher's ordinary session endpoints, as before: the relay adds no new loopback trust.
    - **The auto-mode classifier.** The settings file also carries a `permissions.allow` rule for exactly `$LAUNCHER_RELAY_COMMAND` and sets `FLEET_CONTEXT_FILTER_MODE=off` for that one session: the fleet context filter re-encodes every Bash command before the permission check, so the rule never matched and the classifier decided (and once refused a read-back as `[Auto-Mode Bypass]`). With both, the call is allowed by the rule in milliseconds. A command typed any other way (a pipe, a redirection, a `cd` in front) is not covered and goes back to the classifier. If the classifier refuses it, the bot should say "refused, try again" and run the plain command again, never look for another way round.
    - **States.** `found` / `none`, `resumed` / `opened`, `delivered` / `queued` (the conversation was mid-turn; the launcher submits when it settles, and `ask` stops there rather than pass the turn it was already on off as the answer) / `unconfirmed`, `reply`; and the failures, each its own: `not_found`, `not_this_skill`, `not_resumable`, `stranded` (written but not taken: never send it again), `gone` (the session ended), `host_unreachable` (nothing was done), `unknown` (the launcher could not be reached: delivery unknown), `unavailable` (the reply could not be read, or only a stale one: never old text as new), `no_reply_yet` (sent once, no finished reply in time: read later), `refused` / `relay_off`. When and how the bot uses the relay, and how it words each state in the chat, live in the life-os skill.

- **Board** — one screen answering *"what needs me now, across everything"*: a read-only kanban over five **computed** columns, each holding one kind of card (a card moves because reality changed — there is deliberately no drag-and-drop), laid out in this order: **Backlog** (open GitHub issues), the **Chief's plan** card, **Claude's turn** (live sessions working / idle / unknown / finished-clean), **Your turn** (sessions stalled, blocked on a decision, or otherwise waiting on your input — the only column that needs you), **PRs and jobs** (open PRs plus today's failed or stuck job runs), and **Done today** (today's closed issues, latest close first, ordered by GitHub's close time rather than last activity). The page header's status line names only the exceptions in their tone colour, two at most — `6 questions · 1 needs you` (the chief's unanswered questions, then Your turn), or `1 failing` (failed or stuck jobs) — fleet-wide whatever the project filter shows, and otherwise the plain totals (`3 sessions · 12 issues`). The **Board tab in the nav carries a badge** with what waits on you, from every tab: the chief's unanswered questions plus the Your-turn count (none at 0; the tab's accessible name says "Board, 2 waiting"). Off the Board it counts from the sessions poll, which runs everywhere and carries `chief_questions` (the unanswered count, fleet-wide, or `null` when the plan can't be read); on the Board from the Board's own payload. A plan that can't be read adds no question count anywhere, never a zero. Like every other tab, the Board is built from cards. There is no Dispatch or chief card: the fleet chief lives in its row under Code › Sessions. The Board opens with a toolbar row holding the **project filter** (it narrows every lane, hides jobs, keeps repo-less plan rows) and the **↻ GitHub refresh**, then one collapsible card per column with its count in the header (the *Your turn* count highlights when nonzero). A folded lane says what is wrong instead of its count: *PRs and jobs* shows `1 failing`, the chief's plan `1 question for you`. A source that is down or stale (GitHub, the session-host, the hooks' state file) shows as one attention banner above the lanes. On the phone the lanes stack, with the two live columns open and the GitHub-fed ones folded; desktop lays the lanes side by side, open, one column per lane that holds rows, and folds an empty lane into a one-line strip under them (its title, count, why it is empty and its one action). Every row is the shared action-row: a one-line title (an ellipsis on every width, the full text in its tooltip, on the GitHub page or in a session's drawer) and one meta line that ends in a date (a Done card's close time, a Backlog issue's or PR's last-updated time; the clock for today, `14 Oct` for another day, in your local time), with a chip only for an exception (a failed job's red `failed`, a stuck one's amber `stuck`). While ↻ refreshes GitHub its glyph spins at full strength. The Board carries no Telegram row: Code and Life cover the channel sessions. Directly above *Claude's turn*, in both layouts, sits the **Chief's plan** card: what the fleet chief is doing and intends to do next, read from the plan file it keeps (`chief_plan_file`, format v1, written by fleet-config's `chief_ops.py plan`). It lists what is waiting on you first, one line per question with its ref and a chevron: the first three, then an *N more questions* row that unfolds the rest, then an **Answer N questions** button. Tapping a question opens the answer sheet on that question; the button opens it at the top. The one-shot answer sheet holds every question with its repo, detail and options (the recommended one labelled), an Other field on each, and an Anything-else box with the Chat composer's dictation and image paste; **Done** sends the chief one message holding every answer. Then come the chief's **Lanes (n)** (repo, current item, status), its **Queue (n)** in order (the `queued`, `building`, `gate` and any other status), and **Parked (n)** (`parked` and `waiting-roberto` items, folded on a phone), each count in its heading (no change to the plan file's format, the split is by each item's `status`). A muted line under Queue says the plan lists only what the chief has scheduled while the Backlog counts every open issue. Each row is two lines: the title on its own, then `repo#N · model` with the status chip (an unknown status gets a neutral one) at that line's right end; a row with a `repo#N` ref opens its GitHub issue on a tap and carries a chevron, one without a ref stays inert. The card also says when the plan was last updated. When no chief session is running it says *Chief not running*, and *Chief status unknown* when the session list can't be read, so an old plan never reads as current. With no plan the card stays blank; a plan it can't read adds a quiet *Plan unreadable* note and no error. It refreshes with the Board's own poll. See [Board tab](board.md) for the columns' exact data sources, the agent-aware session-state join, and the transcript/conversation-source hierarchy.
  - **Presence & ghost suppression** — the session-host list is authoritative for launcher-owned presence and agent identity; [`fleet-config`](https://github.com/ferraroroberto/fleet-config)'s sessions-state file is only a semantic overlay. An unmatched external row is suppressed outright once it fails two deterministic ghost checks (its own session is no longer live, or its transcript is already claimed by a live matched card) before falling back to a transcript-recent-activity window — so a missing cloud/bridge transcript or a hard-kill leftover can't claim work for 24 hours.
  - **Backlog rows & the in-progress marker** — the Backlog lane opens with **Start with**, the model the rows launch with. Each row has one **▶ Start** verb (a plain glyph, no tint fill) and a **⋮** kebab holding **YOLO (start and ship)**, **Open on GitHub** and **Copy link** (YOLO takes two taps now); tapping the row opens the issue. Git state is not drawn here any more — it lives on Code › Projects. A `active-issues.json` lifecycle marker (written by `fleet-config`'s issue workflows) gives an issue already in flight an accent **in progress** chip, hides its ▶ and disables YOLO; a missing, corrupt, or stale (>24h) marker degrades to an ordinary actionable row. A marker whose owner lane is provably gone reads "stale claim" and stays startable; an unverifiable owner keeps the lock, labelled "in progress (unverified)". The lane's footer says how fresh the GitHub cache is (`GitHub · updated 3 min ago`).
  - **Drill-down drawer** — tapping a live session opens an inline drawer: the last exchange, the same shared composer as the session view (🎤 mic · ⌨️ keys / 🖼 image · ➤ send — keys stay disabled there, since the Board opens no terminal socket), then 💬 **Chat**, the one tinted primary, with ⌨ **Terminal** beside it and a **⋮** kebab holding ✏️ Rename and Stop (was four equal buttons) — in one row wherever the drawer is wide enough, Chat and the kebab above Terminal in a narrow desktop Board column, so none drops under the 44px floor. The last exchange renders as markdown, with Chat mode's renderer. **Stop** (the unified stop path) always asks first in the themed confirm sheet: the chief and a Telegram session keep their own words, any other session gets a plain "Stop <name>?". Rename opens the same **Rename / link** dialog as the Coding tab, and shows the same provider-native link for a live Claude session — the Board payload carries `web_url` too, so a session the Coding tab links is never *Not available yet* here. Detached sessions get the composer too: a reply is typed into the PC console with the "Sent, not confirmed" wording. An action a session can't take (Terminal for a detached session, Chat for an agent with no transcript reader) stays in the row, disabled, and a tap toasts why. The conversation preview is agent-aware — structured Claude/Codex history wins when it correlates safely, the launcher's own PTY capture is the fallback — and all parsing happens on the drawer request, never the 5 s poll.
  - **The fleet chief** — its home is the **chief row** under Code › Sessions (the Board has no chief card or chat bar): **Start** and **Resume** on the row while it is stopped, **Restart** and **Chief settings** in its kebab, and a tap on the running chief opens its session view, whose composer (with dictation) sends it a message. On the Board the chief shows only as its crowned session row in *Claude's turn*, whose drawer composer reaches it too, and the Chief's plan answer sheet sends to it. The chief is a standing **fleet chief** (Tailscale-only + passkey-gated; there is no free-text Add / Build / Yolo mode any more) — a conversational orchestrator you can ask *"what's open in app-launcher?"* by voice and then direct (*"ok start 229"*) in the same conversation. The chief is a normal PTY session (crown-marked, confirm-before-kill everywhere it appears) spawned in the `fleet-config` checkout so its brain — the `/chief` skill versioned there — loads while app-launcher's own context never does. It comes back via the answer sheet's lazy ensure or a manual Start/Restart (a graceful stop-then-respawn that hands its own compact-and-continue handover log to the fresh session), and the kebab's **Chief settings** opens **Settings › Chief**, the one place for its model, worker cap and auto-compact threshold. There is deliberately no scheduled restart — an unattended one would discard a live batch's context instead of protecting it, so a chief restart is a deliberate operator action only. A chief spawned outside `ensure` self-heals its label from the PTY's first submitted line or Claude Code's own persisted conversation identity, so the Board, the worker cap, and `fleet-config`'s lookup never lose track of it.
  - The Board carries **no usage meter**: usage stays on the Code tab's Usage card, and `/api/board` carries no quota. Board session cards use the shared session row too: avatar and alive badge, the title, and `repo · status · age`; a stalled session carries a red `stalled` chip, and no card is dimmed or edged by its status.

The **Apps** tab is backed by a registry file (`config/apps.json`); the **Jobs** tab by `config/jobs.json`. The **Coding** and **Life OS** tabs need no registry — they list directories live. **Settings** (opened from any page header's ⚙ gear; not a tab and not an always-visible panel) holds the occasional-use actions as **iOS-style inset groups**: each row shows its current value and a chevron and opens a sheet with a back button, a ✕ and one **Done**, and every field saves as it changes (a text or number field when you leave it, with a toast, and an inline message under it when the value is out of range or refused). **Activity**: **Screen time**, how long the launcher was on screen, like the phone's Screen Time. The row reads today's total; its sheet has a **Today · 7 days · 30 days** period, the total (and the daily average over several days), daily bars split by device class (PC solid, phone striped, tablet dotted), the time per device and the time per section (Coding, Board, Life OS, Jobs, Apps, Settings, plus Other for time before the first tab of a visit). Nothing new is recorded: `GET /api/usage/time`, the vendored usage log's foreground-time route, computes it from the visit start and end events the page already logs, merging overlaps so a minute on two devices counts once in the total (and once on each device). Known undercount: on a PC a stretch of more than 15 minutes with no page event counts as 15 minutes, so long typing in a terminal (keys are not events) counts short; phone and tablet visits are trusted, since the screen lock hides the page. The sheet's one primary is **Send to task-os**: it sends the last 7 completed days to task-os's Time tracker now, and the line above it says when that last worked, why the newest try failed, or that the export is not set up (see [Screen time to task-os](../README.md#screen-time-to-task-os)). **Appearance**: Text size (inline) and Usage meter. **Agents**: Launch defaults and Chief (model, worker cap, auto-compact; the Board's chief gear and the chief row's *Chief settings* open it). **Connections**: Telegram, Context filter, API tokens. **This PC**: Folders (the **Projects folder** and its **Hidden projects** list, the Apps, Life OS and fleet-config folders; Scan for new apps lives on the Apps tab), **Passkeys** (terminal-access enrollment), Terminal (history lines, large-file limit) and Start at log on (an inline switch). Each Settings field carries one help line saying what it is for. Settings follows the same contract as the tabs. Its header line names a problem the pane shows (**Telegram: 1 missing** while a profile needs setup, **Telegram unreadable** when the setup status could not be read). When nothing is wrong it shows the running build, **Build a1b2c3d**, and the full build line with its time stays at the bottom of the pane. **Text size** is one segmented control (same `app-launcher.textsize` key and pre-paint boot). The selected tab is remembered per device (`app-launcher.tab`), so a reload or PWA relaunch reopens it, and a reload from Settings reopens the last tab; Code is the first-launch default, and the default when storage is unavailable.
