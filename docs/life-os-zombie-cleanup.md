# Life OS zombie cleanup (#1738)

A Life OS skill session opened by mistake loads the skill's context and posts its greeting, and the capture pipeline then records it as a real conversation. A nightly Job finds those **zombies** and removes them, so the history stops filling up with empty conversations.

- **What a zombie is.** A capture with no `**You**:` block at all: the launcher's own skill-load prompt is already dropped from a capture, so nothing the owner typed follows the greeting. Because that filter is a loose pattern, a real first message that looks like a heading could be dropped too, so a second bound applies: more than 2 assistant blocks, or a body over 16 KB, is **kept** (a greeting is short). The rules are `classify` in `src/life_os_zombies.py`.
- **Never a zombie** (kept): a conversation open in a running launcher session (the same two signals the Delete route checks); a capture younger than the grace window (2 h) or dated in the future; any capture with a user turn. **Skipped, not touched:** an unreadable capture, one with no valid native session id, an oversized one (over the launch size cap), one with no parsable turn. If the session host can't be asked the run stands down: nothing is touched, and the summary says `not confirmed` instead of `0 removed`.
- **Command:** `launcher.py life-os-zombie-cleanup [--mode backup|delete|dry-run] [--grace-hours 2] [--max-per-run 25] [--retention-days 30]`. `backup` (the default) moves each zombie's capture, its Claude transcript (and sidecar folder) and its `index.json` row / `index.md` block into the backup; `delete` removes them through the same routine as the Delete button (`src/life_os_delete.py`, shared with `DELETE /api/life-os/skills/{id}/conversations`); `dry-run` classifies and prints counts, touching and sending nothing. More than `--max-per-run` zombies in one run trips a breaker (nothing touched, exit `3`): that is what a change in the capture parser would look like. A capture that changed between classification and removal is dropped. Exit codes: `1` a capture failed, `2` bad arguments, `3` breaker tripped, `4` session host unknown (declared `deferred` in the sample job).
- **Nightly:** the sample is `life-os-zombie-cleanup` in `config/jobs.sample.json` (daily 04:00, `--mode backup`, alert on failure). The mode is the one word in the job's `args`, edited in the Jobs tab; a missing flag means `backup`, the safe one.
- **Rollout:** weeks 1–2 in `backup`, checking the daily counts and spot-checking the backup folder; then change `backup` to `delete`; backups older than the retention then age out by themselves.
- **Backup layout:** `<runtime root>/app-launcher/life-os-zombie-backup/<YYYY-MM-DD>/<skill>/` holds the capture, `<sid>.jsonl`, `<sid>/` and `<capture>.md.manifest.json` (skill, agent, session id, the transcript's project folder, the verbatim index row and block, the title). It sits outside the Life OS tree so the capture pipeline never sees it. **Retention:** every non-dry run purges dated folders older than `--retention-days` (default 30); only direct children whose name is a date are touched.
- **Restore:** `launcher.py life-os-zombie-cleanup --restore <date>[/<skill>[/<capture file>]]` lists what the backup holds; add `--yes` to put it back. It moves the capture and transcript to where they were, re-inserts the saved index row and block, restores the title and rebuilds the search index, and **refuses** (touching nothing) if a file with the same name or session id has appeared since.
- **Telegram:** one message per non-dry run through the Settings Telegram values (a missing config is a no-op): `Zombie cleanup (mode=backup): 3 removed, 2 kept (live/grace), 1 skipped`. **Counts only**: capture names embed the conversation's own words, so names never go to the chat. Info-level logs carry skill id and file name per removal, never a body.
- **First run:** `--mode dry-run`, compare the zombie count with what you expect, then the first `backup` run.
